ttc-mcp Architecture

How the server is layered, what each layer stores, how a request moves through it, where it runs, and the order to build it in. Everything here is fixed by spec v0.6 (decisions a to j).

Spec docs/spec.md v0.6Runtime Python 3.12, FastMCP 3, Cloud RunStore SQLite in a bucketDate 2026-09-13

Deployment model

One Cloud Run service behind a Google OAuth gate, scaling to zero between questions. It fetches what a question needs, caches it for as long as the feed itself stays unchanged, and keeps the last good copy of everything in case the TTC hiccups. The static store is built elsewhere, by a daily job, and pulled in at cold start.

The layers

Sources on the left never talk to tools on the right directly. Adapters normalise each source, the two stores decide when a fetch is allowed to happen, the domain services do the joins, and the tool surface is a thin mapping from MCP calls to those services.

Package layout

One installable package, one entry point, adapters isolated from everything that reasons about the network. Tests are split so the live parity checks can run nightly without the unit suite touching the internet.

Staleness verdicts are computed at answer time: surface real-time past 90 s, subway and NTAS past 60 s, alerts past 10 min, detours past 30 min; static is expiring within 3 days of feed_end_date and expired after it.

Build order

Each phase leaves a working server. Estimates are from the spec: solo first, paired with Claude second.

  1. Static core
    CKAN adapter, streaming GTFS build into SQLite, patterns and run times, aliases, crosswalk, dual-feed window. Tools: find_stops, nearest_stops, stop, station, routes, route_stops, service_hours, scheduled_departures.
    ~1.5 d · ~6 h
  2. Cache and real-time
    cache.py with TTL, single-flight, last-known-good, conditional GET; bustime, gtfsrt, NTAS adapters. Tools: arrivals (with schedule basis), next_trains, vehicles, feed_status.
    ~1 d · ~4 h
  3. Advisories and propagation
    alerts.ttc.ca and GTFS-RT alerts adapters, disruption engine (closure spans, station id OR code joins), service_status, disruptions attached to every answer.
    ~4 h · ~2 h
  4. Connections
    Direct and one-transfer search over patterns, running-now filter, scoring, disruption overlay with shuttle legs, live first-leg departures. Twenty-trip quality check.
    ~1 d · ~3 to 4 h
  5. Detours, geometry, accessibility, crowding, service changes
    TripModifications adapter and detours tool; route_shape; accessibility with unit-code joins; crowding labels; service_changes parsing.
    ~1.5 d · ~5 h
  6. Cloud deploy
    OAuth client and redirect URI, three secrets, service account, bucket, Artifact Registry repo, Job + Scheduler, first deploy, connector added on claude.ai and Claude Code, egress check against every TTC host.
    ~4 h · ~2 h
  7. Parity tests and hardening
    Nightly live parity suite, 403/429 logging with backoff, NTAS coverage sampling for Line 6, first board-period transition watched in late October.
    ~4 h · ~2 h

Boundaries

  • No geocoding. Addresses become coordinates in the Google Maps MCP; this server starts at nearest_stops.
  • No pollers, no public access. Single user behind the email gate; an idle instance makes no requests and scales to zero. Polling would have cost about 14,000 requests and 4 GB a day for nobody.
  • No timetable-exact itineraries. connections gives structural options with typical minutes and live first-leg departures; a RAPTOR planner over stop_times is a possible later addition.
  • No subway or LRT vehicle positions, no LRT trip updates. The TTC does not publish them; rail answers come from NTAS with the timetable as the stated fallback.
  • No invented reasons. A detour with no matching service change is shown with reason: null; an empty NTAS list is "no prediction", never "no trains".
