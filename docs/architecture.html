Today the server is a local process: Claude Code starts it over stdio, and it reads a store built on this Mac. Phase 5 moves it to one Cloud Run service behind a Google OAuth gate, scaling to zero between questions, with the store built by a daily job and pulled in at cold start.

The layers

Sources on the left never talk to tools on the right directly. Adapters normalise each source, the two stores decide when a fetch may happen, the domain services do the joins, and each tool is a thin mapping from an MCP call to those services. Every box carries the phase that built it.

Boundaries

  • No geocoding. Addresses become coordinates in the Google Maps MCP; this server starts at nearest_stops or a {lat, lon} given to connections.
  • No pollers, no public access. Single user behind the email gate; an idle instance makes no requests and scales to zero. Polling would have cost about 14,000 requests and 4 GB a day for nobody.
  • No timetable-exact itineraries. connections gives structural options with typical minutes and live first-leg departures; a RAPTOR planner over the timetable is a possible later addition.
  • No subway or LRT vehicle positions, no LRT trip updates. The TTC does not publish them; rail answers come from NTAS with the timetable as the stated fallback.
  • No invented reasons. A detour with no matching service change is shown with reason: null; an empty NTAS list is "no prediction", never "no trains".
