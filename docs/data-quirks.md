# Live data quirks the code encodes

Facts about the TTC's data that the code depends on, each verified live (2026-10-05, 2026-10-11, 2026-10-14, 2026-10-15 and 2026-10-18) and none of them visible from the feeds' documentation. Moved here from the README on 2026-10-12; `CLAUDE.md` names the seven an agent trips on first, and spec section 11 holds the dated evidence.

- `alerts.ttc.ca` stamps Toronto local time with a `Z` suffix; `childAlerts` start times match the GTFS-RT per-night entity epochs only when read as local. Year 1 (`0001-01-01`) means open-ended.
- `getallroutesandstopsalerts` no longer carries a `serviceChanges` key; the route changes are GTFS-RT `MODIFIED_SERVICE` entities, so `service_changes` reads those first and merges ttc.ca rows when they reappear.
- Closures publish their nightly windows as `childAlerts`, whose ids are the GTFS-RT `NO_SERVICE` entities listing the closed platform ids. `active_now` and `suspended` come from those; the `REDUCED_SERVICE` umbrella spans whole days and is never read as "closed now".
- `gtfsrt.ttc.ca/alerts/all` answers JSON unless `?format=binary`; `gtfsrt.ttc.ca/trips/detour` is JSON with no header timestamp (its signal is the HTTP `Date`).
- BusTime's per-stop XML writes direction text with double spaces ("504A  King"); headsign matching collapses whitespace. The vehicle feed reports an explicit `EMPTY` on most vehicles, hence the low-confidence "Not busy".
- Rail `shape_dist_traveled` is in kilometres with the first stop of each trip left blank (surface is in metres); the build picks the unit per shape against its measured length and starts every pattern at 0.
- GTFS-RT `NO_SERVICE` entities list every platform of the affected stations, including other lines' platforms at interchanges (a Line 2 closure lists Line 1's St George and Spadina platforms), so a listing closes a platform only when the entity names no routes or one of the platform's own lines.
- An active closure's `shuttleType` reads "Running" and a planned one "Will Operate"; any other value means no shuttle, and the planner then routes around the closed span or drops the trip.
- NTAS keeps publishing predictions at closed platforms during a closure (Old Mill eastbound "1", Jane westbound "1, 4, 8" inside the Kipling to Jane closure), so a suspended platform is decided by the closure, never by NTAS: `next_min: []`, what NTAS said in `ntas_min`, and a note.
- The TTC's closure station list is the shuttle span inclusive of its ends, and GTFS-RT lists every platform of every listed station; the end stations' open-side platforms are served (trains turn back there), so only the interior is closed and an end station is `reduced` with `role: shuttle_terminus`. A terminal end, or a one-station closure, is closed on both platforms.
- The TTC publishes no shuttle timetable, so `connections` estimates a shuttle leg: the full 5-minute headway, 15 km/h along the closed line's track and a minute at each station, stated in the leg's note; the leg reads `basis: estimate`, the option `estimate: true`, and the option ranks after every option without an estimate. The shuttle's stop is the line's lowest platform id at each station, so one end of each direction shows a pathways transfer between two platforms of one station; that walk stands for reaching the shuttle stop.
- The merged feed lists bus bays and streetcar platforms as children of a station with `wheelchair` 0. A platform is a station child served by a subway or LRT route; the rest are the station's `surface_stops`, and the accessibility summary and step-free verdict read the platforms only (counting the bays had read 31 stations partially accessible).
- Every build logs two index checks as it streams `stop_times` (spec 8 item 20): `[check] patterns split for overtaking` and `[check] stop_times with arrival != departure`, 7 and 0 on S1000542, and ends with three more (spec 8 items 3 and 9): surface-stop suffixes that attach to no station, alert station ids and names that resolve to nothing, and how many elevator and escalator codes in today's alerts match a coded pathway node (10 of 18 on 2026-10-11). `--no-checks` skips the last three; the daily Job's log is where they will be read.
- Every `stop_times` row of the merged feed has `arrival_time == departure_time` (all 7.7 M rows of S1000542), so the planner's index keeps one time per pattern position; 7 of S1000542's (pattern, service) groups have a trip overtaking another and are split so that `bisect` stays valid.
- `gtfsrt.ttc.ca/trips/subway?format=binary` carries routes 1, 2 and 4 only (55 entities in the 2026-10-14 capture), with public platform ids, `stop_sequence` on every update and an arrival time but no departure. Its trip ids seldom sit in their timetable slot: 5 of 55 were within 15 minutes of it, the rest 5 minutes to 17 hours off, so a subway update further than 15 minutes from its position's scheduled time is ignored (`overlay.SUBWAY_DRIFT_S`; the surface feed's limit is two hours, `MAX_DRIFT_S`). One trip id repeats a platform about 8 minutes later (the next train under the same id), so an update behind the trip's last matched position is dropped.
- `bustime.ttc.ca/gtfsrt/trips` carried 1,056 to 1,102 trip updates around 01:00 on 2026-10-15. After midnight the trips running belong to the previous service day: at 00:41 an overlay built on the query day's timetable patched 0 of 1,102 records and one built on the day before's patched 1,068, so each day slice of a `connections` query gets its own overlay. Late at night some vehicles run NEW trips (negative trip ids, no static row): 6 of 28 504 vehicles at 01:20 on 2026-10-15, which `vehicles` shows without a headsign and the planner ignores.
- The detour feed's `selectedTrips` lists every trip of a service group on the detour's dates: on 2026-10-15 its 59 entities emptied 92 (pattern, service) groups of S1000542, so a group a detour emptied is dropped rather than left for `has_service` to read.
- `www.ttc.ca` answers from a Microsoft Azure Application Gateway whose firewall treats Google Cloud's egress differently from a home connection: from a Cloud Run Job in us-east1 the first 35 or so of the build's 235 route-detail requests answered 200 and the rest 403 (an HTML page), and a sequential retry seconds later got 403 on all 235; from a home connection all 235 answer 200 at the same concurrency (2026-10-18). The service's one request per source stays under it; the build keeps a refused route's service level from the store it pulled.
