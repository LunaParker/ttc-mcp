# ttc-mcp

MCP server for the TTC network. `docs/spec.md` is normative: when code and spec disagree, fix one and say which. `docs/data-quirks.md` lists the live data facts the code depends on; spec section 11 is the dated verification log; the README is the user-facing guide (what to ask, hosting, degraded service, licences).

## What this is

An MCP server that lets Claude (or any MCP client) reason about the TTC network as it is right now: stops, stations, routes, arrivals, connections, detours, advisories and accessibility, fetched on demand from the TTC's and the City of Toronto's own endpoints, never polled. Single-user: the maintainer hosts it on Cloud Run behind a Google OAuth gate, or a developer runs it locally over stdio. Nineteen tools in four layers, one module each under `tools/`: static (`find_stops`, `nearest_stops`, `stop`, `station`, `routes`, `route_stops`, `service_hours`, `scheduled_departures`), real-time (`arrivals`, `next_trains`, `vehicles`, `feed_status`), advisory (`alerts`, `service_status`, `detours`, `service_changes`) and derived (`route_shape`, `accessibility`, `connections`). `connections(origin, destination, max_transfers: 0..3 = 3, walk_m = 400, depart_at, arrive_by, window_min = 30, limit = 4)` is timetable-exact since phase 6 (decision k): RAPTOR over the trips themselves, exact times on every leg, up to three transfers, a departure window or an arrival time, live trip updates within an hour of now, closures masked, a running shuttle as an estimated pseudo-route, detoured trips on variant patterns. The spec's map: 1 purpose and principles; 2 architecture (2.1 static layer and board periods, 2.2 on-demand fetch layer, 2.3 advisory sources); 3 identifiers; 4 tools (4.1 core, 4.2 added, 4.3 TTLs, 4.4 normative output schemas); 5 store counts; 6 evidence per decision (6.6 fetch model, 6.7 trip questions and disruptions, 6.8 Lines 5 and 6, 6.9 transport and hosting, 6.10 timetable-exact connections and its constants); 7 the decision record a to k; 8 validation items; 9 implementation notes; 10 effort; 11 the verification log.

## Architecture

- Static path: `adapters/ckan.py` resolves the two CKAN packages and `HEAD`s their ETags; `ttc-mcp-build` (`build.main`, then `static/refresh.ensure_static`) rebuilds on an ETag change through `static/build.build_sqlite` (with `static/timetable.py` packing the planner's index in the same `stop_times` pass) into `static-<feed_version>.sqlite`, listed in `manifest.json` (`static/manifest.py`). `runtime.get_store()` opens a `StaticStore` from the manifest and reopens it only when the listed feeds change (clearing `raptor`'s timetables); `runtime.feed_for()` picks today's `FeedDb`; a missing store is a `StoreUnavailable` error payload, never a crash.
- Real-time path: one adapter per source under `adapters/` (`ckan`, `http`, `bustime_web`, `bustime_rt`, `ntas`, `ttc_alerts`, `gtfsrt_alerts`, `detour_feed`, `ttcapi`, `gtfsrt_trips`), typed records each; `SUBWAY_TRIPS` (`gtfsrt.ttc.ca/trips/subway`, `adapters/gtfsrt_trips.parse_subway_trips`, `Realtime.subway_trips`) and `TRIPS` (`bustime_rt.parse_trips`, every `stop_time_update`) feed the `connections` overlay; `sources.py` fixes each source's TTL, stale window, staleness threshold and timeout; `cache.Cache.get` does TTL, single-flight (one in-flight future per key), conditional GET, last-known-good within `max_stale` (else `SourceUnavailable`) and the backoff hold with 403/429 counts; `realtime.Realtime` is the facade (one method per source, `probe`, `status`) behind the `runtime.get_realtime()` singleton. `domain/` is pure functions over a connection and the snapshot; `tools/` map MCP calls onto them and never touch HTTP.
- Advisory snapshot: `advisory.snapshot(feed)` gathers alerts, GTFS-RT alerts and the detour feed (`realtime.attempt` turns a failed source into an error string), resolves detour groups and builds `Disruptions` once, memoised in `advisory._memo` on the realtime and store identities, the loaded feed versions, the minute and the three fetch times.
- How a tool answers: static tools wrap `static_tools._guard(fn)` (today's feed plus `runtime.meta`) or `_with_advisories(fn)` (the snapshot too, as `meta.advisories`); real-time tools wrap `realtime_tools._aguard` (fn returns payload, hits, source and optionally the snapshot; `runtime.meta_rt` takes the worst cache state and verdict across the hits); advisory tools wrap `advisory_tools._aguard` (snapshot first, meta over its hits plus any extra fetch). `connections` resolves its endpoints and takes the snapshot on the loop (a `depart_at` or `arrive_by` rebuilds `Disruptions` at that time), fetches both trip feeds when the query instant is within an hour of now (`derived_tools._trip_feeds`), then in the worker thread (`_plan`) builds the two day slices (`_slices`), each with its own overlay (`overlay.build`), applies decision h's mask, runs `raptor.plan_window` or `plan_arrive_by` and writes the options through `planner.materialize` and `annotate`; the first rides' `next` rows come back on the loop. `meta` is spec 4.4 (its field list opens section 4).
- Transports: `server.main` builds `create_app(recheck, gate, puller, pull_s)`. stdio checks CKAN at startup (`server._startup_check` around `ensure_static`; a rebuild blocks start, not tool calls, and a failed check is logged while the server starts on the store it has, the CKAN client giving up connecting after 10 s) unless `--no-refresh` or `TTC_MCP_SKIP_REFRESH`, then every 24 h (`RECHECK_S`) in a worker thread through the `server.periodic` lifespan; it never gates. http runs `app.run(transport="http", stateless_http=True, json_response=True)` on `--host 0.0.0.0` and `PORT` at `/mcp`; with `TTC_MCP_STATIC_BUCKET` it pulls the store before it listens (`static/bucket.pull`; a failure stops the start) and again every `TTC_MCP_PULL_S` seconds, and never checks CKAN; without a bucket it keeps the startup check unless skipped and never rechecks.
- Gate (spec 6.9): `gate.build_auth` returns FastMCP's `GoogleProvider` (dynamic client registration, consent remembered); `gate.EmailAllowlist` checks every request for a verified listed email and answers anything else with a JSON-RPC `AuthorizationError`; `gate.client_storage` keeps OAuth state in Firestore (sanitized, prefix `ttc`, Fernet) when `GOOGLE_CLOUD_PROJECT` is set, else in memory. `config.gate_settings` refuses a half-configured gate and is read for http only.
- The static store is one SQLite file per feed under `manifest.json`; two feeds are loaded during a board-period overlap and `StaticStore.lookup_trip` tries both.

## Entities and identifiers

- GTFS `location_type` on `stops`: 0 a boarding stop or platform, 1 a station, 2 an entrance, 3 a pathway node (`domain/network.KINDS`). A rail platform is a station child served by a subway or LRT route (`network.is_rail_platform`, `trains.RAIL_PLATFORMS`); bus bays and streetcar platforms under a station are its `surface_stops`, and `network.station_detail` reads the accessibility summary from the platforms only (decision b).
- The public stop number is the merged GTFS `stop_id` (equal to `stop_code` except 42 rows), canonical in every tool input and output; `arrivals.stop_row` resolves `stop_id OR stop_code`. BusTime's protobuf feeds use the Surface GTFS internal id: the `crosswalk` table (`static/build._load_crosswalk`) maps it to `stop_code`, and `domain/vehicles.py` reads it back. The per-stop XML takes public numbers.
- Stations: 34 carry a synthetic `stop_id` (43265 to 43298) with the legacy id in `stop_code`; alerts.ttc.ca names the legacy id, so `disruptions.station_row` joins `stop_id=? OR stop_code=?` (spec 3). `static/build._attach_orphan_platforms` gives a parentless platform named "<X> Station - ... Platform" to station X when exactly one station has that name; 16081 to Kennedy (Line 5) is today's instance.
- Aliases: `static/aliases.build_aliases` fills `station_aliases` at build time from station names, platform prefixes, "- X Station" surface-stop suffixes within 300 m (`SUFFIX_RADIUS_M`) and the `MANUAL` list (Dundas to TMU and friends); GO suffixes are `external` and never resolve; `resolve_station` ranks manual, station, platform, suffix, then a `LIKE` fallback. A surface stop named "... - X Station" inherits X's closures (`Disruptions.for_stop`).
- Modes: `static/gtfs.mode_of` and `series_of`; Lines 5 and 6 are `lrt` although GTFS types them 0; the rail lines are 1, 2, 4, 5 and 6.
- Feeds and board periods: `manifest.json` lists a `FeedEntry` per feed; `StaticStore.for_date` picks the covering feed with the later start, then version; `lookup_trip` tries today's feed then the others; `Manifest.prune` (only on a build, from `refresh._register`) drops feeds that ended before yesterday. `StaticStore.status` is `expiring` within `EXPIRING_DAYS` (3) of the end date with no newer feed loaded, `expired` after it.
- Patterns: `patterns` (one per route, direction and stop sequence; `rank` 1 is the most-used pattern per route and direction and there is no rank 0, since `static/build` increments before it writes the row) and `pattern_stops` (`pos`, `secs` median from the start, `dist_m` along the shape); `departures` is the per-stop timetable (`static/schedule.departures_at`); `station_members` and `transfers` (150 m) give the planner's footpaths at the walk formula (`static/schema.py`). Schema 3 (`SCHEMA_VERSION`; an older store is skipped and named) adds `raptor_groups` (one row per pattern, service id and overtaking split: int32 departure columns, one per position, and the trip ids) and `station_paths` (platform-to-platform seconds from a Dijkstra over each station's pathways, fare gates excluded, overriding the walk formula), both built by `ttc-mcp-build`, which logs `[check] patterns split for overtaking` and `[check] stop_times with arrival != departure`.
- The disruptions element (spec 4.4) comes from `domain/disruptions.element` (an `Alert`; kinds in `adapters/ttc_alerts.KINDS`: closure, suspension, detour, rsz, elevator, escalator, delay, other) or `detour_elements` (detour groups); `source` is `alerts.ttc.ca`, `detour feed` or `gtfsrt alerts`; `element_key` dedupes. `Disruptions` indexes elements by station, stop and route and holds a connection getter, so a snapshot built on the loop is readable from worker threads.
- Closure span model (spec 6.7 item 4): `Disruptions.station_service`, `platform_served`, `shuttle_terminus`, `_at` and `platform_closed_now` in `domain/disruptions.py`; `trains.suspended`.
- Connections (spec 6.10, decision k): `domain/raptor.py` (`Timetable`, `Group` and `Headway`, `Slice`, `Closed`, `plan`, the drivers `plan_window` and `plan_arrive_by`, `has_service`; `timetable_for` keeps one per feed, cleared by `raptor.reset()` from `runtime.reset()` and on a store reopen), `ttc_mcp/overlay.py` (`build`, `patch_groups`, `detour_variants`, `shuttle_routes`, `public_updates`, `Locator`; `_memo` holds an overlay per feed and service day, two days a feed, and `_prep` a fetch's preparation per feed; `reset()` from `runtime.reset()`), `planner.closed_for`, `materialize` and `annotate` (with `resolve_endpoint`, `_closed_positions` and `_touch`), and `derived_tools._slices`, `_plan` and `_trip_feeds`.
- Disruption semantics (closure spans, served end platforms, suspended platforms, shuttle legs) live in `domain/disruptions.py`, `domain/planner.py` and `ttc_mcp/overlay.py` and are specified in spec 6.7 and 6.10. Change them there, never in a tool.

## Design decisions you must not undo

- On-demand fetching, no pollers (decision g, spec 6.6): nothing fetches until a tool asks; the only timers are the stdio CKAN recheck and the http bucket pull. Static data comes only from CKAN by ETag (principle 1) and every request carries the project User-Agent (principle 7).
- The decision record, spec 7: a `route_shape` is an encoded polyline by default (6.1); b station accessibility derives from the rail platforms (6.2); c `trips.wheelchair_accessible` is ignored (6.2); d crowding rides inline on every arrivals row (6.3); e a detour with no matching reason keeps `reason: null` (6.4); f staleness thresholds of 90 s, 60 s, 10 min and 30 min, static `expiring` for 3 days (6.5); g the fetch model (6.6); h trip questions: `nearest_stops` as the bridge from an external geocoder, `connections`, `service_status`, propagation into every answer, the alias table, geocoding out of scope (6.7); i the scheduled fallback with `basis` on every arrivals-style row and NTAS coverage in `feed_status` (6.8); j FastMCP streamable HTTP, stateless JSON, in-process gate, Cloud Run in us-east1, stdio for local use (6.9); k timetable-exact `connections` on RAPTOR (6.10).
- Python 3.14 through uv (`.python-version`; `pyproject.toml` requires 3.13 or later); `fastmcp>=4.1,<5` (4.1.0 in the lock since 2026-10-11; FastMCP 4 sits on MCP SDK v2 and the sessionless 2026-07-28 protocol); the wheel ships `ttc_mcp` only.
- Style: dense one-line statements, ruff `line-length` 160 with `E501` and `E741` off (`l` names a leg in the planner); the formatter is not adopted.
- The store is opened `mode=ro&immutable=1` with one connection per thread (`static/store.open_ro`; the `FeedDb.conn` property on a `threading.local`, closed by a finalizer when the thread exits or by `close`); never pass a connection to another thread, pass `Disruptions.build` a getter.
- Decision k (spec 6.10): plain Python over `array('i')` columns and `bisect`, arrays never Python ints; the index lives in the store (`raptor_groups`, `station_paths`, schema 3), built with the store (`ttc-mcp-build`, or the stdio server's CKAN check), never at query time; the server loads it once per feed (0.1 s, about 65 MB) into an immutable `Timetable` that worker threads share without locks; everything live sits in a per-query `Overlay` in front of it; a ride is `basis: realtime` only when an update was applied to its trip; a shuttle leg is `basis: estimate` with its assumptions in the note and the option `estimate: true`, ranked last. The budget is 250 ms p95 for the planner core on the committed grid (`scripts/bench_raptor.py`, validation item 17).
- The planner runs in a worker thread (`tools/derived_tools._plan` through `asyncio.to_thread`) and builds its slices, overlays and `closed_for` closures there, each slice on its own feed's connection (pattern ids are per feed); `_input_error` bounds `walk_m`, `limit` and `window_min`, checks that `depart_at` and `arrive_by` parse and exclude each other, so bad input never reaches it. `static/refresh._run` runs the ttc.ca fetch from inside a running loop the same way.
- Bucket ordering (`static/bucket.py`): `push` uploads the feeds first and `manifest.json` last, and `pull` stages each feed in a `.part` file, writes the manifest after the feeds, then removes unlisted `static-*.sqlite` files, so a reader never sees a manifest naming a feed that has not landed.
- Unit tests stay offline, and the http transport stays stateless JSON so an idle client never keeps an instance billing (spec 6.9).
- Licences (spec 9, README "Data sources and licences"): the code is MIT (`LICENSE.md`, declared in `pyproject.toml` and copied into the image). The GTFS packages and the two GTFS-RT hosts are TTC open data under the Open Government Licence - Toronto; NTAS, `alerts.ttc.ca`, `ttc.ca/ttcapi` and the BusTime stop-prediction JSP sit behind the TTC's website, which publishes no terms specific to them; its website terms of use cover its pages and don't say whether they reach these endpoints. `server.INSTRUCTIONS` ends with the attribution, the licence link and that split (`test_instructions_carry_the_licence_attribution_and_the_best_effort_wording` pins it): keep them.

## Live-data gotchas

`docs/data-quirks.md` is the full list, verified live on 2026-10-05, 2026-10-11, 2026-10-14 and 2026-10-15. The seven an agent trips on first:

- alerts.ttc.ca stamps Toronto local time with a `Z` suffix: `adapters/ttc_alerts.local_time` strips the `Z` and attaches `America/Toronto`; year 1 means open-ended. Never parse a raw alert stamp as UTC.
- GTFS-RT `NO_SERVICE` entities list every platform of every listed station, other lines' platforms at interchanges included: `Disruptions.platform_closed_now` closes a platform from a listing only when the entity names no routes or one of the platform's own lines; the span rule decides at closure stations.
- NTAS keeps publishing predictions at closed platforms: the closure decides (`trains.suspended`, `SUSPENDED_NOTE`), `next_min: []` with NTAS's numbers in `ntas_min` and no `basis`; an empty NTAS answer is `no_prediction` with timetable minutes, never "no trains".
- ttc.ca's `getallroutesandstopsalerts` has no `serviceChanges` key as of 2026-10-11: `domain/service_changes.py` reads GTFS-RT `MODIFIED_SERVICE` entities first and merges ttc.ca rows by title if the key returns; `adapters/ttcapi.parse_service_changes` tolerates its absence.
- Four TTC hosts answer 403 to Python's default User-Agent: `config.DEFAULT_UA` goes on every client (`adapters/http.make_async_client`, `adapters/ckan.make_client`). The unit suite's MockTransport never sees it, so a live 403 shows only in `feed_status` (`status_counts`, `retry_after`).
- The subway trip feed (`gtfsrt.ttc.ca/trips/subway?format=binary`, routes 1, 2 and 4, 55 entities in the 2026-10-14 capture) gives arrival times only, `stop_sequence` on every update and public platform ids, and its trip ids seldom sit in their timetable slot (5 of 55 within 15 minutes, the rest 5 minutes to 17 hours off): `overlay.SUBWAY_DRIFT_S` (15 min) ignores the rest, against `MAX_DRIFT_S` (2 h) for the surface feed, and `position_of` drops an update behind the last matched position (one trip id repeats a platform about 8 minutes later for the next train). After midnight the running trips are the previous service day's, so each day slice builds its own overlay.
- Every `stop_times` row has `arrival_time == departure_time` (the build's `[check] stop_times with arrival != departure` prints 0), so the index keeps one time per position; 7 (pattern, service) groups of S1000542 have overtaking trips (`[check] patterns split for overtaking: 7`) and are split so `bisect` stays valid, and a patched group is re-split only when a live trip passes a neighbour.

## Deployment practices

- Local stdio: build a store once (`uv run ttc-mcp-build`), then `uv run ttc-mcp --transport stdio`. Claude Code's `.mcp.json` entry is `{"mcpServers": {"ttc": {"command": "uv", "args": ["run", "--project", "<repo>", "ttc-mcp", "--transport", "stdio"]}}}` (the repo's `.mcp.json` is untracked, git-ignored and exists on the maintainer's machine only).
- Local http: `TTC_MCP_SKIP_REFRESH=1 uv run ttc-mcp --transport http`, then `POST http://127.0.0.1:8080/mcp` with `Accept: application/json, text/event-stream`; no gate unless `GOOGLE_OAUTH_CLIENT_ID` is set. The integration suite boots this shape as a subprocess (`tests/integration/conftest.py`).
- The image (`Dockerfile`): `ghcr.io/astral-sh/uv:python3.14-bookworm-slim` pinned by digest; `uv sync --frozen --no-dev --extra cloud` in two layers, dependencies then the project as a non-editable wheel with `--reinstall-package ttc-mcp`; `ENV TTC_MCP_TRANSPORT=http TTC_MCP_SKIP_REFRESH=1 TTC_MCP_CACHE=/data PORT=8080`; `CMD /app/.venv/bin/ttc-mcp`. One image, two commands: the Job overrides the command with `/app/.venv/bin/ttc-mcp-build --bucket <bucket>`. Never `python -m ttc_mcp...` from `/app`, where the uncompiled source copy shadows the wheel. `scripts/smoke_image.sh` is CI's image job: build, assert `sqlite3.threadsafety` is 3, build the fixture store in a container, serve it with `TTC_MCP_NOW=2026-10-06T08:00`, assert the 19 tools exactly and a `routes` answer from `/data`; it fails closed.
- Cloud Run (spec 6.9; `docs/deploy.md` is the paste-and-run runbook with the values table): project `$PROJECT_ID` ($PROJECT_NUMBER; runbook step 1 sets both, and a maintainer's own values can sit in an untracked `CLAUDE.local.md`), everything in `us-east1`; service `ttc-mcp` (`--allow-unauthenticated`, the gate is the app; min 0, max 1, 2 GiB, cpu-boost, gen2) at `https://ttc-mcp-$PROJECT_NUMBER.us-east1.run.app/mcp`; Job `ttc-mcp-static` from the same image, fired by Cloud Scheduler `ttc-mcp-static-daily` at 04:30 Toronto; bucket `gs://ttc-mcp-static-$PROJECT_NUMBER`; two service accounts, `ttc-mcp-sa` for the service (reads) and `ttc-mcp-job-sa` for the Job and the Scheduler (writes the bucket); secrets `ttc-mcp-oauth-client-secret`, `ttc-mcp-jwt-signing-key`, `ttc-mcp-storage-fernet-key`; images in Artifact Registry repo `ttc-mcp`, one tag per deploy. The Job's filesystem is in memory, so both zips and both stores count against its `--memory` (2 GiB since schema 3); after a schema bump the Job runs on the new image before the service answers.
- Nothing is deployed as of 2026-10-15. Phase 5b is the runbook's first run (`docs/cloud-run.md` is its build specification); validation items 14 to 16 wait for it. When it lands, update the runbook's first line, spec 6.9 and section 11.
- Billing: the project's hard-cap budget and `billing-killswitch` cover it, no new budget wiring; the cap is project-wide, so check headroom before provisioning (runbook step 1). Expected marginal cost is near zero.

## Working here

### Commands

- `uv sync --extra cloud` (Python 3.14 from `.python-version`; the extra brings the Firestore state store and GCS, and the unit suite's GCS wiring test imports `google.api_core`). `uv run pytest` runs the unit suite in `tests/unit` on the fixture store built from `tests/fixtures/gtfs-mini.zip`.
- `uv run pytest tests/integration` boots the real server and reaches the TTC's hosts; it is deliberately not in CI.
- `uv run ruff check .` is the lint CI runs. The formatter is not adopted; the dense style is deliberate.
- `uv run ttc-mcp-build` builds the static store into `~/.cache/ttc-mcp` (CKAN download and build with the ttc.ca service-level fetch, about a minute on a fast connection, 40 s in a container on 2026-10-12; `--no-ttcapi` skips it, `--from-zip` builds from a local feed, `--bucket` runs the Job's pull and push). A store is schema 3 (139 MB for S1000542, built in 17 to 18 s from the cached zips); its log carries `[check] patterns split for overtaking` and `[check] stop_times with arrival != departure`. Live smoke scripts live in `scripts/` and run with `TTC_MCP_SKIP_REFRESH=1`; `scripts/smoke_image.sh` needs Docker.
- `scripts/bench_raptor.py` holds the planner to the 250 ms p95 budget (validation item 17) on the committed grid (the 20 validation pairs at 08:00, 17:30, 23:30 and 01:00 on tomorrow's timetable; instant, 30- and 60-minute windows, arrive-by) and exits 1 over it. It needs a schema-3 store with the crosswalk: `uv run ttc-mcp-build --cache <dir> --from-zip <merged.zip> --surface-zip <surface.zip> --no-checks` from the zips in `~/.cache/ttc-mcp/downloads/`, then `TTC_MCP_CACHE=<dir>`. `--live` adds the snapshot and the trip-update overlay at four instants from now and prints warm and cold per mode without a verdict: a now-anchored night grid runs over the budget before any overlay exists (sparse service weakens the arrival bound), and a cold overlay build costs about 100 ms a query with 1,000 surface records, so the verdict stays on the committed grid. `scripts/validate_connections.py --before <capture.json> --depart <instant>` compares the 20 pairs with an earlier capture of their answers in the v0.7 contract (`typical_min` per option).
- `uv run scripts/make_logo.py` redraws `docs/logo/`: the README logo and its dark variant, the icon (SVG, PNG at 1024, 512, 192 and 32) and the 1280 by 640 social card that GitHub's Settings > Social preview takes by upload. It runs in its own environment from the script's pinned inline dependencies, sets Inter 4.001 (fetched by commit and checksum into `~/.cache/ttc-mcp/fonts`, or `--font`) as outlines, and takes TTC Red `#DA251D` and Black `#0A0B0C` from the TTC's signage standards; its output is committed, and a change to the logo is a change to the script, rerun.
- PyCharm run configurations: `Tests`, `Integration (live)`, `Server (stdio)`, `Build static`.

### How work lands

- Test first: a failing test, then the change. One commit per behaviour, plain subject line, the why in the body, no attribution lines.
- Branch, pull request, merge when CI is green. Pushes and pull requests happen on the maintainer's say-so.
- Comments at most two lines; the why belongs in the commit body. Pull request descriptions: at most one paragraph and five bullets.
- Spec edits ride with the change that needs them; a live finding gets a dated line in section 11.
- CI (`.github/workflows/ci.yml`, pushes to main and pull requests) is four jobs: unit (`uv sync --frozen --extra cloud`, `pytest tests/unit`), lint (`ruff check`), build (sdist and wheel, both entry points called from a clean venv) and image (`scripts/smoke_image.sh`); all four green is the merge rule. Dependabot (`.github/dependabot.yml`) watches GitHub Actions, uv (grouped) and the Docker base image weekly.
- The SDD workflow: phase plans are working documents and are not committed; task briefs, reports and ledgers sit under `.superpowers/`, which git ignores (its `sdd/.gitignore` is `*`). The decisions and evidence a phase produces land in the spec (sections 6, 7 and 11).

### Known deferred items

- Expired feeds stay in the manifest until the next build (`Manifest.prune` runs only inside `refresh._register`), and nothing deletes bucket objects: `bucket.pull` removes local `static-*.sqlite` files the manifest dropped, but old objects stay in the bucket.
- `advisory._memo` keys on `id(store)` and `id(rt_)` and holds one entry; a test that swaps the store or the realtime object should call `advisory.reset()`, since ids can be reused after collection. `overlay._memo` and `_prep` key on the ids of their inputs and hold the inputs so the ids stay theirs, and `raptor._cache` on the feed version and path; `overlay.reset()` and `raptor.reset()` clear them (both run in `runtime.reset()` and when `runtime.get_store` reopens on a feed change).
- Phase 6 left out (spec 6.10): step-free routing, true range RAPTOR, reverse RAPTOR and NEW trips (negative ids, no static row; 6 of 28 504 vehicles ran one at 01:20 on 2026-10-15). `raptor.has_service` ignores shuttles, so an endpoint only a shuttle serves reads no service; the shuttle pseudo-route is scanned on both day slices; a `depart_at` or `arrive_by` query rebuilds `Disruptions`, so the overlay memo misses on it. Three build levers were measured and not taken: one patch pass for both days, mapping stops through `stop_of` instead of rebuilding the crosswalked records, and keeping per-feed trip reads across fetches. An endpoint at a variant-backed skipped stop keeps that stop alone, so if a live entity ever covered every trip of the only route there, the answer would be a no-service note instead of the served stops around it.
- Time-aware closure spans (a closure that starts or ends inside a window or an arrive-by search): closures are evaluated at the query instant and `derived_tools._closure_notes` names such a closure in the answer when an option rides its line (spec 6.10).
- Estimated shuttle labels prune like exact ones in `raptor.py` (`best`, `target`, the per-round dominance), so an exact alternative with at least as many transfers that arrives after an optimistic estimate is never found; "estimates rank last" orders the survivors (spec 6.10).
- Arrive-by's empty-answer `has_service` check reads the target's day (`q.t0`), not the first instant of the four-hour search, so an early-morning arrive-by can say no service while the search span had some.
- An arrive-by answer's head omits `window_min`, though its step-back window is `window_min` (30 by default) in `derived_tools._plan`.
- `overlay.patch_groups` copies every column of a group whose trips were only masked; sharing the schedule's columns when nothing moved would trim the cold build.
- The network guard covers httpx only; google-cloud-storage, urllib and raw sockets are unguarded, which is why `tests/unit/test_bucket.py` injects a fake client into `GcsBlobs`.
